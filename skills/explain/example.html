Part 1 The intuition

In this part: what exists, what we want, and what stands in the way.

What we HAVE

Think of a small library. The shelves hold the books; a card catalog by the door tells you where each one sits. The catalog exists only so nobody has to walk every aisle. Every card was copied from a book that was on a shelf at the time.

In the libraryIn notekeeper
The books on the shelvesThe .md files in notes/
A catalog cardA row in the FTS5 index
The librarian's morning walkReconciliation at startup
A card for a book that was returned to a different branchA row whose file is gone
The load-bearing fact The index is derived data — the files are the truth. Anything in the index can be thrown away and rebuilt from the notes folder. Nothing in the notes folder can be rebuilt from the index. Every decision below follows from that asymmetry.

What we WANT

Notes change behind the application's back — a git pull, a sync client, an editor open in another window. We want the next startup to notice, quietly bring the index back in line with the folder, and never show the user a search result that points at something that isn't there.

What's IN THE WAY

  1. You git pull a branch that deletes twelve old meeting notes.
  2. notekeeper starts. Its index still holds a row for each of them.
  3. You search invoice. Three of the hits are those deleted notes.
  4. You press Enter on one. The app opens a path that no longer exists.
What the user actually saw A traceback — FileNotFoundError: notes/2023-q2-invoice.md — from a search result the app itself had just offered. The only known workaround on the issue tracker was rm .notekeeper/index.db, which throws away the whole index and costs a full reindex of several thousand notes.

Part 2 The idea of the fix

In this part: the whole fix in one sentence, and why it's right.

The fix, in one sentence At startup, walk the notes folder once, delete every index row that walk did not see, and reindex the files whose timestamp or size changed.

Why that's right:

  • It follows the asymmetry. Deleting a derived row costs a reindex of one file; deleting a note costs the note. Only one of those is recoverable, and the fix only ever does that one.
  • It is proportional. The old workaround discarded the entire index for a handful of stale rows; this discards exactly the stale rows.
  • It is idempotent. Running reconciliation twice changes nothing the second time, so a crash mid-startup is not a special case.
  • It keeps the failure where it belongs. Search results now describe files that existed moments ago, so the crash has no way to reach the user.

The design rests on one distinction — not every mismatch means the same thing:

Resolvable divergenceMust-abort failure
Looks likeRows for files that moved, changed or vanishedUnknown schema version, corrupt database file
What we knowThe rows are readable and the folder is trustworthyWe cannot reason about the rows at all
ResponseDrop the affected rows, reindex, carry on silentlyRebuild the index from scratch

Part 3 The twist

In this part: the subtlety that separates a naive fix from the real one.

The obvious implementation reads the index row by row and asks the filesystem about each one: stat() the path, and if that raises, the file is gone — drop the row. It is one loop, it needs no scan, and it is wrong.

It is wrong because a missing file and an unanswerable question look identical from inside that loop. During an atomic save the note exists as a temp file under another name for a few milliseconds. A sync client does the same thing. A permissions blip on a network share does the same thing.

Why that's poisonous Save a note at the wrong instant during startup and its row is deleted — permanently, as far as the user can tell, because nothing will reindex that file until it changes again. The note is still on disk and still opens fine; it has simply stopped appearing in search. There is no error, no log line, and no way to reproduce it on demand. The index appears to forget things at random.
The rule A row may only be deleted on the authority of a completed directory scan, never on a single failed stat(). Unknown is not the same as absent. If the scan itself looks untrustworthy — no entries found in a folder that is not empty — we abandon reconciliation and change nothing.

Review caught this: the first version of the patch was the row-by-row loop, and the reviewer's question was simply "what does a failed stat mean here?". That question is why the shipped version scans first.

Part 4 The details: reading the code

In this part: the final shipped code, block by block.

def scan_notes(root: Path) -> dict[str, Stamp]:
    """One pass over the notes tree. The only authority on what exists."""
    seen = {}
    for path in root.rglob("*.md"):
        st = path.stat()          # inside the walk: the entry existed
        seen[str(path.relative_to(root))] = Stamp(st.st_mtime_ns, st.st_size)
    return seen

Plain English: walk the folder once and write down every note we can see, with its timestamp and size.

def reconcile(db, root: Path) -> Report:
    disk = scan_notes(root)                  # ← must finish before any DELETE
    if not disk and any(root.iterdir()):
        raise ScanIncomplete(root)           # ← empty scan of a non-empty folder

    rows = db.execute("SELECT rel_path, mtime_ns, size FROM notes").fetchall()
    indexed = {r.rel_path for r in rows}

    gone    = [r.rel_path for r in rows if r.rel_path not in disk]
    changed = [r.rel_path for r in rows
               if r.rel_path in disk
               and disk[r.rel_path] != Stamp(r.mtime_ns, r.size)]

    db.executemany("DELETE FROM notes WHERE rel_path = ?",
                   [(p,) for p in gone + changed])
    # ↑ the Part-3 repair: `gone` is derived from `disk`, which came from the
    #   completed walk — never from a per-row stat() that may simply have failed.

    reindex(db, root, changed + [p for p in disk if p not in indexed])
    return Report(dropped=len(gone), refreshed=len(changed))

Plain English: compare the catalog against what the walk saw; drop the cards the walk couldn't account for, then re-file the changed and brand-new notes.

The ordering is load-bearing, not stylistic. scan_notes() must complete before the first DELETE, because the scan is what turns "I couldn't see this file" into "this file is not there". Move the walk inside the loop and you have rebuilt the naive version exactly.

def open_index(root: Path) -> Db:
    db = connect(root / ".notekeeper" / "index.db")
    if db.user_version != SCHEMA_VERSION:
        rebuild(db, root)      # must-abort class: these rows are unreadable
        return db
    reconcile(db, root)        # resolvable class: readable rows, drifted content
    return db

Plain English: a schema we don't recognise means a full rebuild; a schema we do recognise just needs the morning walk.

def test_deleted_note_leaves_no_search_hit(tmp_path):
    # arrange: index two notes, then delete one behind the app's back
    root = make_notes(tmp_path, {"a.md": "invoice draft",
                                 "b.md": "invoice final"})
    open_index(root)
    (root / "a.md").unlink()

    # act: start again, exactly as the user did after a git pull
    db = open_index(root)

    # assert: the ghost row is gone and search is clean
    assert [h.rel_path for h in search(db, "invoice")] == ["b.md"]

Plain English: delete a note while the app isn't looking, restart, and prove the search no longer offers it.

That test is the evidence, not just a guard: on unpatched code it fails with FileNotFoundError: a.md — the identical traceback from the bug report.

What we deliberately did NOT touch

  • The live file watcher. It handles changes while the app runs and was never the problem; the gap was only the window when the app is closed.
  • The FTS5 schema. Changing it would force every existing user through a full rebuild — the exact cost this fix was written to avoid.
  • The corruption path. rebuild() already existed and already worked. The fix reuses it rather than teaching reconciliation a second job.

Part 5 Mini-glossary

Only the terms used above, in plain words.

FTS5 SQLite's built-in full-text search extension. It keeps its own copy of the text you want searchable, so queries don't have to open your files.
Derived data Anything you could recompute from somewhere else. Deleting it costs time, not information. The opposite is a source of truth.
Atomic save Writing to a temporary file and renaming it over the target, so a reader never sees a half-written file. The side effect is that the target briefly does not exist under its real name.
Reconciliation Comparing two views of the same thing and bringing one back in line with the other. Here: the index is brought in line with the folder.
Idempotent Running it twice has the same effect as running it once. Useful because it makes an interrupted run safe to simply repeat.

Part 6 Defend it

In this part: test yourself, then the answers you'd give under pressure.

Check yourself

Try each one out loud before opening it.

Why is dropping diverged rows not data loss? Because the rows are derived. Every one of them can be rebuilt from the file it came from, and the files are untouched. The only cost is the time to reindex.
Why can't we just stat() each row's file? Because a failed stat() means "I couldn't answer", not "it's gone". An atomic save, a sync client or a permissions blip all produce the same failure as a genuine deletion, and the consequences are wildly different.
What makes the scan more trustworthy than the stat? The scan observes existence positively — a file appeared in the listing. Absence from a completed listing is a statement about the whole folder at one moment. A stat failure is a statement about nothing.
Why raise on an empty scan of a non-empty folder? Because that combination means the walk itself is untrustworthy — a mount that isn't ready, a permissions problem at the root. Acting on it would delete every row in the index. The safe response to an untrustworthy scan is to change nothing.
Why is a schema mismatch handled differently from a stale row? A stale row is readable, so we can reason about exactly which rows are wrong. An unknown schema means we can't read the rows at all, so there is no smaller safe action than a rebuild.

Likely challenges

"Isn't scanning the whole folder at every startup slow?" It's one readdir walk with a stat per file — milliseconds for a few thousand notes, and the reindex it triggers is proportional to what actually changed. The alternative on the issue tracker was rebuilding the entire index, which is orders of magnitude worse.
"What if a note changes during the scan?" Then either the walk sees the old stamp or the new one. If it sees the old one, the file's stamp differs at the next startup and it gets reindexed then. The failure mode is one startup of staleness, which is what we already tolerate; it is not a deleted row.
"Why not just verify lazily, when a search hit is opened?" That fixes the traceback but not the bug. The user still gets offered results that don't exist, and the ranking is still computed over notes that are gone. Reconciliation makes the index honest; a lazy check only makes it quiet.

The 30-second version

"The search index kept rows for notes that had been deleted outside the app, so search would offer a result and then crash opening it. The index is derived data — the files are the truth — so the fix is to walk the notes folder once at startup and drop any row the walk didn't see. The subtlety is that you can't do it per-row with a stat(): a save in progress looks exactly like a deleted file, and you'd silently drop rows for notes that still exist. So deletions are only allowed on the authority of a completed scan. The regression test reproduces the original FileNotFoundError on unpatched code and passes on the fix."
